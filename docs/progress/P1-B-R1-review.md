## 3 剩余阻塞项

行号以最终交付 `0dce6ed` 为准；实施文件仍在远端任务分支，不在 main。

### G01：两次前端构建退出码被忽略

`scripts/check_p1_b.sh:153–169` 的 `build_frontend()` 返回 `run_logged` 的真实构建退出码，但第 168、169 行直接调用，不检查结果、也不调用 `bad()`。脚本只启用 `set -u`。`run_logged()` 自身不会设置全局 fail。

因此存在明确路径：构建生成新二进制后返回 3 → 函数返回 3 被忽略 → 后续执行该二进制通过 → 汇总 fail 仍为 0。删除构建目录不能排除此情况。默认与回绕构建均有此缺口，违反 R1 保留真实构建退出码传播的要求。

需逐配置立即记录失败并阻止运行其产物；用真实构建完成后受控返回 3 的包装验证，即使二进制存在且可运行，构建步骤和实际总入口也必须失败。

### G02：记分板缺少独立 PC 顺序与完整请求载荷检查

`verification/p1b/tb/tb_frontend.cpp:351–363` 从 DUT 的请求 PA 提取 PC，再按该 PC 查镜像；第 399–400 行又用该请求 PC 构造译码期望。`model_pc` 在第 403、410 行被更新，却没有在请求监视/随机循环中用于独立的 PC 比较。

这能验证返回字与实际请求地址一致，**不能证明实际请求地址正确前进**。若随机阶段在 RAM 内跳过或重复一个 PC，响应和译码均与错误请求自洽，队列与计数仍可通过。`wait_accept(pc)` 的明确 PC 检查覆盖基础/部分定向项，不覆盖全部随机请求；有序队列不能替代独立的顺序地址模型。

另外第 272–282、426–430 行请求保持检查只有 PA、ID、gen；包装只暴露这几个请求字段。VA、size、byte_mask、is_store、wdata、cacheable、priv 未纳入观察和稳定性比较，报告中“请求 payload 逐字段稳定比较”的表述过宽。生产 RTL 中这些字段当前为固定值，未发现其实际变化，但原任务要求的完整检查尚未交付。

需让请求 PC 期望独立来自复位、TB 的有效 redirect 与顺序 +4 规则，同时维持取消/异常行为；检查完整有效请求载荷及最终握手边沿。补真实 PC 比较与请求载荷稳定性负向，并保存正常对照。

### G03：负向探针仍能用无关错误冒充指定比较检出

- `verification/p1b/tb/tb_frontend.cpp:926–936` 只要全局 errors 非零，就输出 `NEGATIVE_MISMATCH_DETECTED`；第 1039–1047 行注入流程也只按“注入开关存在 + 任意 errors”输出 `INJECTED_FAIL`。
- `verification/p1b/tb/tb_decode.cpp:190–194` 同样只判断 `tb.errors>0`。
- `scripts/check_p1_b.sh:52–74,201–209` 仅匹配这些通用标记和 exit 1，不核对指定 op 比较错误是否确实出现、是否存在其他错误或是否走完完整流程。

本轮原始日志中的错误确实各为一个 op 比较错误，早期失败保留的事实成立。但探针判据仍不满足 R1“指定错误原因绑定”：若 op 比较检测失效，而身份/顺序/稳定性等其他错误导致非零，负向步骤也可能被算作成功。

需单列指定注入比较与其他错误，成功标记只在预期错误实际发生、其他错误为零且所需流程完成时产生。给出指定错误未检出但出现其他错误、以及指定错误伴随额外错误的受控反例；两者均必须使探针步骤/总入口失败。
