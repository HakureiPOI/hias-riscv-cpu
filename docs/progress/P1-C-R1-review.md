## 3 剩余阻塞项

以下行号以 `5022162` 为准，相关实施仍只在任务分支。

### G01：差分入口仍未复用完整退休格式校验

`scripts/p1c_diff.py:72–103` 手工检查部分字段，未调用冻结的 validate_stream；其余比较/基线也没有 seq 检查。保留正常 PC/指令/Token/寄存器，只把一条 seq 改为重复或缺失，单独差分入口仍可能 PASS。token_valid/next_pc_valid 使用 truthiness，rd_we 在比较时 bool 转换，严格布尔/数值类型、必需字段和来源列表等同样未由该入口统一校验。

正常总入口目前先运行 `check_retire_contract.py --validate-file`，它能拦截这些格式错误；因此不将此描述为正常总入口已绕过格式检查。但 R1 明确要求“纳入同一可复用入口，不靠调用顺序”，直接差分/注入的“干净基线”仍缺少这一层。应复用既有校验函数并统一诊断，不再维护一套较弱的格式子集。

### G02：fault 首次 ARF 快照不能证明进入停止时没有副作用，监视负向未交付

`verification/p1c/tb/tb_faults.cpp:77–84` 在已经看到 fault_valid 后才读取 ARF 保存为 snap_regs，第 149–151 行仅和这个快照比较。它证明随后 16 拍不再变化，**不能证明出现 fault 的边沿之前/当拍没有错误写入**。R1 要求的已提交前缀独立 ARF 镜像没有实现；原先零前缀全零检查也被删除。

明确反例：jalr_unaligned 的前缀使 x1=0x55、x5=7；若异常 JALR 没退休却错误将链接 `0x8000000c` 写入 x1，首次 fault 快照就会保存这个错误值。之后保持 16 拍，当前元数据、计数和快照稳定比较仍可全部通过。现有 RTL 写使能门控静态看符合停止规则；这是检查器的盲点，不声称已观察到该 RTL 缺陷。

fault 元数据也主要证明保持：初始 fault_instr、Token gen 等没有与用例/分配序列独立核对。需要从复位预期及实际正常提交维护完整架构镜像，首次 fault 时就比较，再沿 16 边沿持续比较；元数据初值按用例/生产者身份核对，保持快照只用于后续稳定性。

此外，R1 V03 明确要求至少一个真实副作用/保持/错路监视路径的受控负向；本轮只有差分文件注入/变体，没有该监视器负向证据。补“首次 fault 已存在错误 ARF 值但之后稳定”和“保持期间出现变化”的观察夹具，要求真实监视器按原因拒绝，而不是直接打印失败。
