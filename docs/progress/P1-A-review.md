## 3 必须修复的问题

定位均基于 `dcdb54c`，尚未合入 main。

### F01（高）：34 位地址加法回绕可绕过 RAM 范围限制

定位：`rtl/soc/ram_bridge.sv:65–66,86–92,110–111`。

`in_range` 使用两个 34 位数相加后比较结束地址，没有防溢出，也没有单独要求起始地址 `< RAM_END`。以下自然对齐请求的加法结果均回绕为零：

| PA | 宽度 | 34 位 PA+长度 | 当前判断 | 截断后 RAM 位置 |
| --- | --- | --- | --- | --- |
| `0x3ffffffff` | byte | 0 | 范围通过 | 最后一个字的 lane 3 |
| `0x3fffffffe` | half | 0 | 范围通过 | 最后一个字的 lane 2/3 |
| `0x3fffffffc` | word | 0 | 范围通过 | 最后一个字 |

对应正确 mask/数据时，请求可被认定合法；后续 `pa[16:2]` 将其映射到 RAM 尾部。非法 Store 因此可能真正改写 RAM，高 PA 不再被 PMA 拒绝。现有高 PA 用例只有 `0x180000000`，随机地址不覆盖 34 位顶端，未发现此缺陷。

修复应使用足够宽的端点算术或无溢出的上下界/剩余空间检查，先确认合法宽度再检查完整访问范围；错误请求不得进入实际 RAM 写口。新增上述地址的读/写反例，要求 access fault，预置并回读 RAM 尾字和相邻保护值，证明不被别名修改。

同时补 `size=3` 的非法宽度处理。RTL 当前将它映射成 0 字节、aligned=false，可能误报 misaligned；本项目将非法 size/mask/data 视为接口非法请求，返回相应 load/store access fault。只有有效宽度的自然对齐失败才报告 misaligned。TB 的 `1 << size` 不能把 size=3 当成受支持的八字节访问；该编码须有明确正反检查。

### F02（中）：TB 未验证宣称的稳定性、守恒与错误无副作用，周期计数漏掉事务执行

定位：`verification/p1a/tb/tb_ram_bridge.cpp:131–135,195–279,311–338,399`。

- 响应未 ready 时，TB 每拍覆盖 `got`，最后才比较；未保存第一次有效载荷并逐拍要求 valid/载荷保持。中途 valid 消失、数据变化而握手前恢复可漏检。
- “请求停顿”是将 req_valid 置零等待若干拍，之后才发请求；并非保持 valid=1、让桥 ready=0 后再接受。所有事务串行执行，没有覆盖前一响应背压时下一请求等待、旧响应消费与新请求接受的边界。
- accepted 是布尔量，没有按边沿统一维护“接受请求数/完成响应数/在途集合”，也没有在空闲窗口拒绝多余响应；同一请求重复响应或无主响应缺乏直接检测。Store 写重复相同值无法单靠最终 RAM 内容发现，应观察实际 RAM 写握手/次数。
- 非法请求比较错误响应后没有系统地核对实际写口或回读其可能别名位置；“内存必须不变”的注释不足以证明无副作用。接入独立合法性预期和实际 RAM 写观察，非法请求写次数必须为零；对关键别名位置做回读。
- “Store 接受后不可取消”的说明没有对应 `flush_after_accept=true` 的 Store 调用，只有 Load。补真正接受后的 Store+Flush，并验证写入/响应各一次；同时覆盖未接受请求被 Flush 抑制。
- `cycles` 只在 `tick()` 增加，而 transact 循环直接产生上升沿，未增加 cycles。因此统计和预算没有覆盖大部分事务周期；预算只在测试末尾检查，也不能作为运行中的总周期保护。统一时钟推进与监视入口，所有仿真边沿都计数，并在预算达到时立即非零退出。

补独立请求/响应队列与逐边沿监视，不要求多事务吞吐或另建通用框架。至少给稳定性或重复响应检测器一个受控反例，证明新断言/记分板会因明确原因拒绝，而非只增加通过标记。

### F03（中）：负向执行路径缺少统一、有强制终止兜底的主机看门狗

定位：`scripts/check_p1_a.sh:42–58,116–119`。

正常路径 `run_logged` 有 `timeout -k`；`run_expected` 却直接执行命令，比较负向探针完全没有主机看门狗。挂起探针虽有 `timeout 5s`，但没有 kill-after；被测进程不响应 TERM 时可能一直等。不能依靠 TB 自身的预算覆盖主机执行挂死。

统一为可配置、有限的主机时限与强制终止兜底，保留预期退出码与错误原因核对。若比较探针超时，应判为探针失败，不能当成预期比较失败通过。用受控挂起（含忽略 TERM 的场景）证明步骤与总入口均在边界内非零退出。
