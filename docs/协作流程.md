# 项目管理与 opencode 实施协作流程

生效日期：2026-10-19。用户确认采用手动转交任务的方式。

## 1 职责与环境

| 参与方 | 环境 | 职责 |
| --- | --- | --- |
| 管理与审查方 Codex | 当前 Windows 工作区 | 阅读课程要求、维护设计和任务文档、审查代码与报告、评估证据、调整路线并下达后续任务 |
| 实施方 opencode | 用户提供的 Ubuntu 24 容器 | 检查真实环境、实现 RTL/软件/脚本、执行验证、修复缺陷、提交代码与原始证据 |
| 用户/组长 | 两侧之间 | 手动转交任务与报告位置，落实课程解释、人员分工、板卡和硬件条件 |

管理方不在 Windows 侧代替 opencode 开发 RTL 或运行容器测试，也不因读到“PASS”就认定任务通过。当前没有配置直连容器或自动报告通知；任务单准备好不等于任务已经在容器启动。

## 2 当前任务

P0-01、P0-02、P1-A 与 P1-B 已通过管理验收并合入，当前实施任务为 [P1-C 整数执行与顺序提交](tasks/P1-C-整数执行与顺序提交.md)。opencode 从包含验收/任务单的最新 main 新建 `codex/p1-c-integer-execute`，读取本轮要求并保留已通过的环境、RAM/总线与前端验证；后续当前任务以 README 和最新管理任务单为准。

任务单明确目标、基线、允许修改范围、交付物、验收条件和阶段边界。课程必选项不得由实施方自行删除或改为选做；发现冲突时交回具体问题、证据和建议。

## 3 一轮协作

1. 管理方将任务单提交并推送；用户将启动指令交给 opencode。
2. opencode 获取基线，保护现有修改，在任务分支实现和验证，不重置或删除不相关工作。
3. 实现代码先提交，在该版本上运行检查并保存完整日志；若测试后修改实现，必须提交新版本并复测。
4. opencode 再提交报告与小型证据，推送任务分支，将分支、被测试 Commit、最终 Commit 和报告路径交给用户。
5. 用户将结果转交管理方；管理方读取差异、实现、测试与证据，给出通过、补证据、修复或路线调整结论。
6. 审查通过后再合入主分支；未通过则继续当前任务，不因日期已到自动进入下一阶段。

实现、被测试版本与报告版本可以不同，但对应关系必须明确。报告不能引用尚不存在的“自身 Commit”；推荐记录被测试实现 Commit，最终报告 Commit 由交付消息给出。若报告提交还改变了实现，需针对最终实现重新测试。

## 4 报告与原始证据

报告统一放在 `docs/progress/<任务编号>-report.md`，至少包含：

- 任务编号、执行日期与时区、实际环境、任务基线、分支、被测试实现 Commit。
- 完成内容、文件清单、设计偏离与原因、未完成或未验证内容。
- 每项验证的完整命令、工作目录、版本/配置、种子、退出码、状态与日志路径。
- 失败复现、首个错误、根因与修复；依赖/权限阻塞的实际错误。
- 对阶段门禁的影响、需要管理方决定的问题及建议下一步。

小型日志和结果清单随任务提交到 `verification/evidence/<任务编号>/`。大波形、第三方源码、安装目录和构建二进制不直接加入仓库；另存的大文件需有可访问位置、大小和哈希。只有容器本地路径且管理方无法取得的证据，记为待补充。

“未安装”“未运行”“失败”“通过”分别记录，不能混淆。截图可补充上板证据，不代替可复制的命令和原始日志。

## 5 审查与推进

管理方检查需求、改动范围、代码逻辑、测试有效性和证据对应关系。实际容器执行由 opencode 负责；Windows 侧审查不得声称已经重跑 Linux 验证。

不接受通过删除失败测试、弱化断言、全局屏蔽告警、任意跳过差分或事后修改期望值制造通过。必要豁免说明技术依据并交回审查。参考项目成绩不能充当本项目证据。

opencode 不自行合入 `main`；改变课程范围、阶段目标或共享接口时，先提交问题说明。任务内常规实现选择和必要依赖修复可自主处理并记录，无须逐步等待管理方。

P1-A 基础框架/RAM 总线与 P1-B 取指/译码已按报告、原始证据及管理审查通过，当前下达 P1-C。后续仍逐任务实施、报告、审查再合入，不把取字/译码或框架测试视为 CPU 已运行；P1-C 的整数子集退休差分也不等于完整 P1 出口。板卡、指定 OS 与课程数据等待事项继续单列跟进，不阻止独立工作；没有自动派发给容器或 opencode 的连接。
