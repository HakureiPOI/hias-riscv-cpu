# RISC-V 超标量乱序 CPU 课程实验计划书

**项目名称：** 基于 RISC-V 的超标量乱序处理器设计与实现  
**计划周期：** 2026 年 10 月 19 日—2026 年 12 月 31 日  
**开发方式：** 自主微架构设计、AI 辅助 RTL 开发、开源项目参考、渐进式验证  
**目标平台：** SystemVerilog / Verilator / FPGA（具体开发板待确定）  
**项目状态：** 初始规划阶段

---

## 一、项目背景与总体目标

### 1.1 项目背景

本次计算机体系结构课程设计要求实现具有一定现代处理器特征的 RISC-V CPU，重点涉及超标量乱序执行、分支预测、Cache/TLB 存储系统、浮点运算及硬件验证。

考虑到项目周期有限，同时课程鼓励使用 AI 辅助硬件设计，本项目拟采用“人工确定架构与接口、AI 负责 RTL 实现和部分测试生成、自动化工具负责验证”的开发模式。

项目不以手工逐行编写 RTL 或完整复现开源处理器为目标，而是参考成熟开源设计，构建具有自主微架构和独立验证体系的 CPU。

### 1.2 总体目标

在 2026 年 12 月底前，完成以下主要工作：

1. 设计并实现 RV32 双发射乱序处理器，具有指令获取、译码、寄存器重命名、动态调度、乱序执行和顺序提交能力。
2. 实现 ROB、Issue Queue、多个 ALU，以及精确异常和分支预测失败恢复机制。
3. 实现动态分支预测器及 BTB，并通过测试评估预测准确率。
4. 实现组相联 Cache、分离的 ITLB/DTLB 和 Sv32 地址翻译机制。
5. 独立实现 IEEE 754 单精度浮点加减乘除模块，并完成专项测试。
6. 建立模块测试、程序测试、差分测试和性能测试体系。
7. 完成 FPGA 综合、时序与资源评估，并在开发板条件允许时完成实际运行验证。
8. 整理体系结构设计图、RTL 工程、验证结果、性能分析和实验报告。

**项目成功的判断依据应是可运行 RTL 与客观验证结果，而非代码规模或 AI 生成代码的数量。**

## 二、技术路线与设计原则

### 2.1 技术选型

| 项目 | 规划方案 |
|---|---|
| ISA 基础 | RV32I，计划扩展 M、Zicsr |
| 数据位宽 | 32 bit |
| 硬件语言 | SystemVerilog |
| 微架构 | Tomasulo 风格的动态调度与顺序提交 |
| 前端 | 2-wide Fetch / Decode |
| 后端 | 2-wide Issue / Commit |
| 整数执行 | 至少两个整数 ALU，配合分支与访存功能单元 |
| 寄存器依赖管理 | RAT + ROB Tag |
| ROB | 初始建议 32 项 |
| Issue Queue | 初始建议 8—16 项 |
| 分支预测 | Gshare / 2-bit Counter + BTB |
| Cache | 多路组相联，Write-back + Write-allocate |
| 虚拟内存 | Sv32 |
| TLB | 独立、全相联 ITLB/DTLB |
| FPU | 独立 FP32 Add/Sub/Mul/Div |
| 验证环境 | Verilator、Spike/NEMU、自动化测试 |
| FPGA | 开发板确定后适配 |

上述 ROB、Issue Queue 和 Cache 容量均为初始设计参数，不是不可更改的验收指标。后续可以根据仿真、资源和时序结果调整。

### 2.2 设计原则

**（1）先建立可运行基线，再逐步升级**

每个开发阶段必须保留一个可独立编译、仿真和验证的版本，避免多个复杂模块同时引入后无法定位错误。

**（2）优先满足课程功能，随后考虑性能优化**

初期采用较保守的调度、访存和恢复策略，确保架构正确性，再逐步提升并行度。

**（3）模块化设计，保持接口稳定**

提前定义前后端、执行单元、访存系统及提交接口，尽量使新模块能够替换旧模块，而不需要重新设计整条流水线。

**（4）测试先行，持续回归**

每次修改 RTL 后，至少执行相关模块测试，并在合入主分支前完成整机回归。

**（5）AI 辅助实现，自主确定技术方案**

可以利用 AI 阅读开源代码、生成 RTL、编写 Testbench 和定位缺陷，但设计决策、测试标准、架构取舍以及最终验收由团队负责。

## 四、总体微架构设计

### 4.1 处理器数据通路

计划采用以下总体结构：

```text
                     Branch Predictor
                            |
                            v
              +--------------------------+
              | Fetch / ICache / ITLB    |
              +--------------------------+
                            |
                       2-wide Fetch
                            |
                     Decode / IBuffer
                            |
                       2-wide Decode
                            |
                   Rename / RAT / ROB
                            |
                       Dispatch
                            |
                     Issue Queue
                            |
                 Wakeup / Select Logic
                            |
             +--------------+--------------+
             |              |              |
           ALU 0          ALU 1        Branch / LSU
             |              |              |
             +--------------+--------------+
                            |
                    Writeback / Bypass
                            |
                       ROB Complete
                            |
                     2-wide Commit
                            |
                    Architectural State

      LSU <--> DTLB / Sv32 MMU <--> DCache <--> Memory
```

上述结构为计划方案，实际 RTL 可以对执行单元端口、BRU 和 LSU 发射队列进行适当调整。

### 4.2 乱序执行的关键设计

**寄存器重命名：** 采用 RAT 维护逻辑寄存器与在途生产者的映射，利用 ROB Tag 跟踪未提交结果，消除 WAR/WAW 假依赖。

**动态发射：** Issue Queue 保存待执行指令，监听生产者结果，在操作数与执行单元就绪时选择指令发射。

**顺序提交：** ROB 以程序顺序提交执行结果，对异常、分支预测错误及状态恢复进行统一管理。

**访存顺序：** 初期对未解析的 Store 地址采取保守策略，避免不正确的 Load 越过旧 Store。Store 在提交后才允许产生不可回滚的内存副作用，后续再优化访存并行性。

**精确异常：** 异常指令和相关年轻指令不能错误提交；发生异常时恢复正确的架构状态及控制流。

### 4.3 不同阶段的结构演进

本项目不计划把完整单周期、完整五级流水线、双发射顺序处理器和乱序处理器全部独立重做。

拟采用以下精简路线：

**最小单发射流水线 → 单发射 OoO → 双发射 OoO → BPU/Cache/MMU 集成 → 最终验收**

其中：

- 第一阶段快速完成基础 RV32I 运行能力。
- 第二阶段尽早重构为支持 Rename、ROB、Issue Queue 的 OoO 后端。
- 第三阶段将核心通路扩展至双发射。
- 存储系统、分支预测器和浮点运算单元通过并行模块开发逐步集成。

这条路线可以减少早期顺序流水线设计的大量重复工作。

## 五、分阶段开发计划

### P0：工程初始化与验证基础

**目标：** 建立稳定的开发、仿真和自动化测试环境。

主要任务：

- 初始化自主 CPU 工程目录、构建脚本与 Git 分支管理。
- 确定 RV32 ISA 范围、模块接口和基础数据结构。
- 配置 Verilator、RISC-V 交叉编译工具链和参考模拟器。
- 建立统一的指令退休记录与程序运行结果检查机制。
- 建立模块测试和回归测试的基础框架。

**阶段验收：** RTL 工程能够编译；测试程序能够生成；最小处理器程序可以产生可检查的执行结果。

### P1：最小单发射顺序 CPU

**目标：** 实现具备基础运行能力的 RV32I CPU。

主要任务：

- 完成 PC、取指、译码、寄存器堆、ALU、Load/Store、Writeback。
- 实现基本流水线寄存器及 Valid/Stall/Flush 控制。
- 实现数据冒险检测与必要的 Forwarding。
- 支持基本分支、跳转与简单程序运行。
- 建立 RV32I 指令测试基线。

**阶段验收：** 常用 RV32I 指令及简单 C 程序通过验证；无已知架构状态不一致。

### P2：单发射乱序执行

**目标：** 建立真正支持乱序执行的处理器后端。

主要任务：

- 实现 RAT、ROB、Issue Queue。
- 实现 Tag 分配、操作数等待、结果广播和唤醒选择。
- 增加多个整数执行通路。
- 实现乱序完成、顺序提交。
- 实现异常、分支错误及 Flush 时的状态恢复。
- 建立 OoO 专项 Testbench。

**阶段验收：**

- 能够观察到年轻指令先于旧指令完成执行。
- ROB 退休顺序保持正确。
- 处理 RAW/WAR/WAW 依赖。
- Flush 后没有错误路径指令提交。
- 定向测试及整机回归通过。

### P3：双发射乱序执行

**目标：** 达到课程要求的主要超标量能力。

主要任务：

- 将取指、译码、重命名和提交扩展至至少 2-wide。
- 支持每周期最多发射两条可执行指令。
- 处理同周期多指令之间的寄存器依赖。
- 扩展执行结果回传及 ROB 完成端口。
- 实现双提交情况下的异常优先级与精确状态更新。
- 统计每周期 Fetch/Issue/Commit 数量。

**阶段验收：**

- 实际出现双发射与双提交。
- 同周期 WAW/RAW 等边界场景正确。
- 多执行单元并发运行正常。
- 功能测试与 DiffTest 通过。

### P4：动态分支预测

**目标：** 实现动态预测、目标预测及错误恢复。

主要任务：

- 实现 2-bit Saturating Counter 或 Gshare。
- 实现 BTB。
- 处理预测命中、目标错误和方向错误。
- 将预测结果与 Fetch、BRU、ROB 连接。
- 测量预测准确率与分支预测失败次数。

**阶段验收：** 在指定测试集上取得超过 70% 的预测准确率，并记录统计口径；预测错误恢复后程序执行正确。

进阶内容可考虑 RAS、更复杂的混合预测及 Checkpoint，但不纳入初始关键路径。

### P5：Cache 与虚拟内存系统

**目标：** 实现课程要求的 Cache、TLB 和地址转换。

**Cache 部分：**

- 实现 ICache / DCache。
- 实现组相联结构及并行 Tag/Data 访问。
- DCache 采用 Write-back + Write-allocate。
- 实现替换策略、Cache Miss、Refill、Dirty Eviction。
- 评估 Bank、流水化或其他缓存优化方案，选择至少一项实现。

**MMU/TLB 部分：**

- 实现 Sv32 两级页表转换。
- 实现相互独立的全相联 ITLB / DTLB。
- 实现 TLB Miss、Page Table Walk、表项替换。
- 实现相关权限检查、Page Fault、`satp` 及 `SFENCE.VMA` 等必要语义。
- 补充所需的 M/S 特权状态、CSR 与异常处理能力。

**阶段验收：** Cache 和 TLB 定向测试通过，地址翻译、权限、异常及流水线恢复正确；缓存结构具备可综合实现。

### P6：独立 IEEE 754 FPU

**目标：** 优先完成独立浮点计算单元，暂不以完整 RV32F 集成为强制前提。

主要任务：

- 定义统一 FPU 输入/输出接口及握手机制。
- 实现单精度浮点加法、减法、乘法、除法。
- 实现规格化、舍入及异常标志。
- 覆盖 NaN、Infinity、零、非规格化数、溢出、下溢等情况。
- 对除法等长延迟计算实现适当的执行控制。
- 建立与独立软件参考结果的自动比对。

**阶段验收：** 独立 FPU 模块能够完成上述运算，专项随机测试和边界测试通过，输出结果及异常标志满足声明支持的 IEEE 754 语义。

**扩展目标：** 若时间允许，进一步完成浮点寄存器、指令译码、`fcsr` 和 OoO 执行路径集成，支持 RV32F 程序运行。

### P7：整体集成、性能与 FPGA 验证

**目标：** 完成最终课程验收。

主要任务：

- 整体功能回归与性能测试。
- 统计 IPC、CPI、周期数、提交宽度利用率。
- 统计分支预测命中率与 Cache/TLB 行为。
- 完成 RTL 综合、资源分析和时序约束检查。
- 根据实际开发板完成时钟、复位、存储器及 IO 接口适配。
- 运行 FPGA 测试程序。
- 整理架构图、模块设计文档和实验报告。

**阶段验收：** 形成可提交、可演示、可重复验证的完整工程，并明确记录未完成或未验证的功能。

## 七、验证体系与验收标准

### 7.1 分层验证体系

采用四级验证：

**第一级：RTL 静态检查**

Verilator Lint、可综合性检查、模块接口与参数检查。

**第二级：模块级 Testbench**

针对 ALU、RAT、ROB、Issue Queue、BPU、Cache、TLB、FPU 独立测试，覆盖 Reset、Flush、边界条件与并发冲突。

**第三级：CPU 程序与差分测试**

使用 RV32I 测试程序、定向汇编、随机程序，按照指令退休记录与 Spike/NEMU 等参考模型对比。涉及异常和 CSR 的测试需要正确配置参考模型与执行环境。

**第四级：综合、性能及 FPGA 验证**

记录资源消耗、时序、IPC、分支预测准确率和缓存统计；具备开发板时进行实际运行测试。

### 7.2 关键验收指标

| 验收方向 | 核心要求 | 验证证据 |
|---|---|---|
| 超标量 | 至少 2-wide Fetch/Issue/Commit | 并发测试与宽度利用率统计 |
| 乱序执行 | Rename、Issue、ROB、多 ALU | 乱序完成及顺序提交日志 |
| 精确异常 | Trap 与流水线恢复正确 | 异常、Flush 定向测试 |
| 分支预测 | 动态预测、BTB，准确率高于 70% | 测试程序及预测统计 |
| Cache | 组相联、WB/WA、并行 Tag/Data | Miss/Refill/Writeback 测试 |
| TLB/MMU | 分离全相联 TLB、Sv32 | 地址转换、Page Fault 测试 |
| FPU | IEEE 754 FP32 加减乘除 | 参考结果比对与边界测试 |
| 性能 | IPC/CPI 等指标可测量 | Benchmark、Profile |
| FPGA | 综合、时序和实际验证 | 工具报告、上板结果 |
| 文档 | 架构、模块、测试与问题记录 | 设计报告及可复现脚本 |

上述各项需要以正式课程指导书及后续助教解释为最终验收依据，尤其是 FPU 是否必须集成完整 RISC-V F 扩展、FPGA 的具体演示形式等尚未确认的部分。

## 八、AI 辅助开发与工程管理

### 8.1 AI 的使用方式

AI 主要承担：

- 参考架构源码与规范解读；
- RTL 模块生成、修改和重构；
- Testbench 与断言生成；
- 编译和仿真错误分析；
- 回归测试脚本生成；
- 设计文档、接口说明及模块框图整理。

团队主要承担：

- 技术选型与微架构决策；
- ISA 范围和接口标准确定；
- 审查 AI 输出的设计；
- 验证测试结果是否真实可靠；
- 管理跨模块依赖与集成；
- 处理 FPGA 实机问题和最终验收。

### 8.2 单模块开发流程

每项任务按照以下流程实施：

**功能规格 → 接口定义 → 测试设计 → AI 生成 RTL → Lint → 模块仿真 → 整机回归 → 代码审查 → 合入主分支**

为了避免 AI 在修复局部问题时破坏其他模块，原则上每次任务应明确允许修改的文件范围。

AI 不得随意删除失败测试、降低断言强度，或仅通过修改测试期望值制造通过结果。

## 十、主要风险与应对措施

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 顺序升级 OoO 需要大量重构 | 影响核心进度 | P1 保持最小规模，尽早进入 OoO 设计 |
| 双发射依赖与提交逻辑复杂 | 功能错误难定位 | 先验证单发射 OoO，再扩展宽度 |
| AI RTL 存在隐蔽时序缺陷 | 仿真通过但 Corner Case 失败 | 测试先行、断言、差分、持续回归 |
| Cache/MMU 与 LSU 耦合 | 集成周期延长 | 预先定义请求/响应接口 |
| FPU 舍入与特殊值复杂 | IEEE 754 正确性不足 | 使用独立参考模型与大量边界测试 |
| FPGA 板卡尚未确定 | 综合和上板进度不可控 | 尽早确认设备，提前进行综合测试 |
| 多模块并行修改产生冲突 | 工程集成困难 | 接口冻结、独立分支、阶段门禁 |
| 开源参考与原创性边界不清 | 影响课程验收 | 记录来源，独立设计主体架构 |

### 10.1 进度控制策略

设立三个重要检查点：

**11 月 15 日：** 单发射 OoO 应具备基本可验证能力。如果未达到，优先收敛 Rename/ROB/Issue，不继续堆叠功能。

**11 月 29 日：** 双发射 OoO 应形成稳定基线。如果仍存在重大正确性问题，应暂停非必要性能优化，将工作重点转向修复和回归。

**12 月 13 日：** Cache、TLB、Sv32 等必须进入整机验证。此后原则上不再进行大规模微架构重构，优先完成课程验收与 FPGA 集成。

若时间不足，应优先取消 TAGE、复杂预测恢复、多级 Cache 优化等进阶目标，而不是直接舍弃课程要求的核心功能。无法完成的必选项目须在最终报告中明确说明，不得以未经验证的实现替代验收结果。

## 十三、总结

本项目采用 **RV32 双发射乱序 CPU 自主开发、AI 辅助 RTL 实现、开源架构参考和持续验证** 的总体路线。

开发过程中，以最小顺序处理器快速建立运行基础，随后集中完成 ROB、寄存器重命名、动态发射和双发射提交等核心功能。动态分支预测、Cache/TLB 和独立 FPU 作为后续阶段及并行任务推进，并逐步完成整机集成。

项目的主要技术挑战预计集中在乱序执行正确性、双发射依赖处理、精确异常恢复以及存储系统集成，而非基础 RTL 语法。

在整个实施过程中，应坚持**功能正确性优先、逐阶段验收、测试结果可追溯**，避免因 AI 快速生成大量代码而造成无法管理的集成风险。

最终目标是在 2026 年 12 月底前形成一款具有明确自主设计内容、完整实验记录、可运行 RTL 与可验证硬件实现的 RISC-V 超标量乱序处理器。
